# Standalone deployment

```text
Browser -> AuthBoundry -> Existing Application
```

AuthBoundry owns the external socket, strips inbound authority headers, derives
a fresh context and denies unknown route policies. The placement changes. The
authority model does not.

## Upstream trust contract

Standalone mode has an explicit trust boundary:

```text
untrusted client request
        ↓
AuthBoundry authentication and authorization
        ↓
trusted upstream request
```

For every request forwarded to the upstream application, AuthBoundry guarantees:

1. inbound `x-authboundry-*` headers are removed before authentication
2. authentication is performed before protected routes are forwarded
3. principal, tenant, claims, capabilities and delegation are reconstructed from
   AuthBoundry-owned state
4. verified authority headers are generated by AuthBoundry
5. unauthorized requests are rejected and are not forwarded
6. paths outside the configured route policy are rejected and are not forwarded

The upstream application must be reachable only through this configured
AuthBoundry boundary when it relies on AuthBoundry authority headers.
`x-authboundry-*` headers are not independently self-authenticating credentials;
their authority derives from the trusted AuthBoundry-to-upstream transport and
deployment boundary.

AuthBoundry injects the following reserved header vocabulary from the verified
context:

| Header | Meaning |
| --- | --- |
| `x-authboundry-principal` | verified principal id |
| `x-authboundry-principal-kind` | verified principal kind |
| `x-authboundry-tenant` | verified tenant id |
| `x-authboundry-claims` | verified claims projection |
| `x-authboundry-capabilities` | verified capabilities projection |
| `x-authboundry-delegation` | verified delegation id, when delegated |
| `x-authboundry-delegated-by` | verified delegator id, when delegated |
| `x-authboundry-context` | serialized verified context |
| `x-authboundry-signature` | context digest used by the example upstream |
| `x-authboundry-proxy-signature` | proxy digest used by the example upstream |

Applications may read these headers only after the direct-bypass deployment
requirement is satisfied. Header extraction is not a standalone authentication
mechanism.

Adoption begins configured but unattached. A standalone attachment requires an
explicit, reachable upstream:

```sh
authboundry attach --upstream http://localhost:9000
authboundry status
authboundry verify
authboundry serve
```

The upstream is an explicit HTTP or HTTPS origin with a port, not a route.
AuthBoundry preserves the configured hostname (`localhost`, IPv4 or bracketed
IPv6), resolves it at connection time and uses that same origin for proxying.

With no attachment, `serve` exposes only authority endpoints and states clearly
that it is not protecting an application. With an attachment, startup fails
closed if the application target cannot be reached.

## Canonical topologies

Development keeps both sockets local:

```text
Browser
   ↓
127.0.0.1:8787
AuthBoundry
   ↓
127.0.0.1:3000
Application
```

In production, public traffic reaches AuthBoundry and the application is private:

```text
Internet
   ↓
AuthBoundry
   ↓
private upstream network
   ↓
Application
```

Use network-level isolation, loopback/private binding, container networking or
the existing platform controls to keep the upstream application from being an
independently reachable public authentication boundary. If an external client can
connect directly to the upstream, the upstream must not treat
`x-authboundry-*` headers as authority.

## Framework-neutral integration

An application behind the trusted boundary can consume the verified projection in
whatever framework it already uses:

```js
const principalId = request.headers.get("x-authboundry-principal");
if (!principalId) {
  return unauthorized();
}

const tenantId = request.headers.get("x-authboundry-tenant");
const state = await getStateForTenant(tenantId, principalId);
```

This pattern is valid only for an application deployed behind the trusted
AuthBoundry upstream boundary. Do not use header extraction as an authentication
mechanism for a directly exposed application.

## Linux standalone runtime

The package release matrix includes standalone native runtimes for Linux and
macOS:

| Operating system | Architecture | Package |
| --- | --- | --- |
| Linux | x64 | `@authboundry/core-linux-x64` |
| Linux | arm64 | `@authboundry/core-linux-arm64` |
| macOS | x64 | `@authboundry/core-darwin-x64` |
| macOS | arm64 | `@authboundry/core-darwin-arm64` |

For unreleased or source-built validation on Linux, build and run the Rust
workspace binary with Cargo before relying on it as a packaged runtime.
